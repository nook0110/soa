# Архитектура маркетплейса

## Описание проекта

Это учебный проект маркетплейса - платформы, где продавцы размещают товары, а покупатели их заказывают. Реализована микросервисная архитектура с разделением на отдельные сервисы.

## Домены и их ответственность

### 1. Управление пользователями (User Management)
- Регистрация и авторизация
- Управление профилями покупателей и продавцов
- Хранит: данные пользователей, токены сессий

### 2. Каталог товаров (Product Catalog)
- Добавление и редактирование товаров продавцами
- Поиск и фильтрация товаров
- Управление остатками
- Хранит: товары, категории, количество на складе

### 3. Заказы (Order Management)
- Создание заказов
- Отслеживание статусов
- Хранит: заказы, состав заказов, статусы

### 4. Платежи (Payment)
- Обработка платежей
- Учет транзакций
- Хранит: платежи, способы оплаты

### 5. Уведомления (Notifications)
- Отправка email/SMS о статусах заказов
- Хранит: шаблоны уведомлений, логи отправки

### 6. Рекомендации (Recommendations)
- Персонализированная лента товаров на основе истории просмотров
- Хранит: история действий пользователей, предпочтения

## Варианты архитектурной декомпозиции

При проектировании рассматривались три варианта разбиения системы.

### Вариант 1: Монолит

Все функции в одном приложении с одной базой данных.

**Плюсы:**
- Простота разработки и деплоя
- Нет проблем с распределенными транзакциями
- Легко дебажить
- Быстрее разработать MVP

**Минусы:**
- Нельзя масштабировать отдельные части
- Один баг может положить всю систему
- Сложно работать большой командой (конфликты в коде)
- Долгий деплой даже при маленьких изменениях

**Trade-off:** Простота разработки vs масштабируемость и надежность

### Вариант 2: Микросервисы по доменам (выбран)

Каждый домен - отдельный сервис со своей БД.

**Плюсы:**
- Можно масштабировать только нужные части (например, product-service при большой нагрузке)
- Падение одного сервиса не роняет всю систему
- Разные команды могут работать независимо
- Можно использовать разные технологии для разных сервисов

**Минусы:**
- Сложнее разрабатывать (нужна синхронизация между сервисами)
- Нужна инфраструктура (API Gateway, очереди сообщений)
- Сложнее дебажить распределенные ошибки
- Eventual consistency вместо ACID транзакций

**Trade-off:** Гибкость и масштабируемость vs сложность разработки

### Вариант 3: Модульный монолит

Один деплой, но код разделен на модули с четкими границами.

**Плюсы:**
- Проще чем микросервисы, но структурированнее монолита
- Можно потом разделить на микросервисы
- Есть транзакции
- Легче дебажить

**Минусы:**
- Все равно нельзя масштабировать части отдельно
- Риск размытия границ между модулями
- Один деплой для всего

**Trade-off:** Баланс между простотой и структурированностью

## Обоснование выбора

Выбрал **Вариант 2 (микросервисы)** по следующим причинам:

1. **Требование персонализации** - recommendation-service будет нагружен вычислениями, его нужно масштабировать отдельно

2. **Разная нагрузка** - product-service будет получать много запросов на чтение (просмотр товаров), а order-service - мало но важных запросов на запись

3. **Безопасность платежей** - payment-service должен быть изолирован для соответствия PCI DSS

4. **Уведомления асинхронно** - notification-service работает через очередь, логично выделить отдельно

Монолит был бы проще, но не подходит под требования масштабируемости и персонализации. Модульный монолит - компромисс, но не решает проблему разной нагрузки на части системы.

## Распределение по сервисам

В итоговой архитектуре каждый домен - отдельный сервис:

- **user-service** - изолированная авторизация, можно масштабировать отдельно
- **product-service** - много запросов на чтение, нужно кэширование
- **order-service** - основная бизнес-логика, требует транзакционности
- **payment-service** - изолирован для безопасности (PCI DSS)
- **notification-service** - асинхронная обработка, работает через очередь
- **recommendation-service** - тяжелые вычисления, отдельное масштабирование

## Границы владения данными

Каждый сервис владеет своей БД:

| Сервис | База данных | Что хранит |
|--------|-------------|------------|
| user-service | users_db | Пользователи, роли, сессии |
| product-service | products_db | Товары, категории, остатки |
| order-service | orders_db | Заказы, позиции заказов |
| payment-service | payments_db | Платежи, транзакции |
| notification-service | notifications_db | Логи уведомлений |
| recommendation-service | recommendations_db | История просмотров |

**Важно:** Нет общих баз между сервисами. Каждый сервис работает только со своими данными.

## Взаимодействие сервисов

### Синхронное (REST API):
- Пользователь → Product Service: получить список товаров
- Order Service → Product Service: проверить наличие товара
- Order Service → Payment Service: провести оплату
- Order Service → User Service: проверить пользователя

### Асинхронное (RabbitMQ):
- Order Service → Notification Service: отправить уведомление о заказе
- Order Service → Recommendation Service: обновить историю покупок

## Технологии

- Python 3.11 + Flask
- MySQL 8.0
- RabbitMQ (для асинхронности)
- Docker + Docker Compose

## Диаграмма

C4 Container диаграмма находится в файле `workspace.c4` (формат LikeC4).

## Запуск проекта

### Требования
- Docker
- Docker Compose

### Команды

Запустить сервис:
```bash
docker compose up --build
```

Проверить работу:
```bash
curl http://localhost:5000/health
```

Ожидаемый ответ:
```json
{
  "status": "healthy",
  "service": "product-service",
  "timestamp": "2024-01-01T12:00:00Z"
}
```

Остановить:
```bash
docker compose down
```
